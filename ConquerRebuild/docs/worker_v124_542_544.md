### 1.2 Item creation

- **itemtype source**: 0x140126228-0x14012623f `action->vtable[0x10](4)` — the *same* getter that
  returns the action type at index 3 (0x140123671/0x14012367f), i.e. **cq_action/cq_newaction
  record value index 4** (the type itself is index 3). Nothing is read from the payload for it.
- 0x140126245-0x14012626c call `FUN_14034a8d0(user, itemtype, r8w = rsp+0xb0 (arg13),
  r9b = 1, stack arg5 = 1, arg6 = 0, arg7(byte) = 1)`; inside `FUN_14034a8d0` the 5th stack arg
  becomes the amount passed on (0x14034a98f/0x14034a9e0) and the 7th stack arg is the
  `test sil` flag at 0x14034a98a.
  `FUN_14034a8d0` is **`CUser::AwardItem`** — its own log string at 0x14034a963 is
  `"CUser::AwardItem, user(%s,%u) itemtype(%u), item from: %d"`; on full bag it prints
  `"STR_FULLBAG_NO_MORE"` (0x14034aa38) and returns 0.
- 0x140126276 `mgr->vtable[0x60](mgr, AwardItem_result)` = `GetItemTemplate(index)` -> item.

## 2. Type 543 — 0x140126496 .. 0x140126560 (no sscanf; check-then-remove item)

### 2.1 Input
No `sscanf` at all: the only input is the caller-supplied 10th argument
`edx = [rsp+0x818]` (0x14012649e) = the dispatcher's 6th stack arg (r12 at 0x140146454;
loaded from `[rsp+0x1168]` in `FUN_140145f60`). Used as the **item-template index**:
`mgr->vtable[0x60](mgr, idx)` at 0x1401264a8. Because it is a template index, it is an
**itemtype**, not an item instance id. Its provenance inside the dispatcher (which packet field
fills `[rsp+0x1168]`) = **UNKNOWN** (not resolved here).

### 2.3 The item-removal call `FUN_140340190`
user_item.cpp function; first statement is `CHECKF "nAmount > 0"` (0x1403401bd, line 0x339E),
and the same function contains the log
`"User[%u][%s] ForgeItem Erase SolidifyItem[%u] failed"` (0x1403406e6, gmlog `gmlog/ForgeItem`
at 0x1403406ed). So it is the **CUser item-remove/destroy path (amount + solidify/undo flag)**,
called here with amount **1**. Exact public name of the method = UNKNOWN (decompile has no symbol),
but the assertion texts and the gmlog tag identify it as the "remove item (forge/solidify aware)"
routine.

### 2.4 Packets built by 543
Not in the case body. The removal routine `FUN_140340190` sends over
`[vtable+0x350]` (single-client) at 0x1403404?? region (send slots 0x1403414de, 0x14034183a);
the actual CMsg builders are shared with the give-item path (`FUN_1400f83e0` ctor /
`FUN_1400f8490` 1009 builder / `FUN_1400f8430` dtor) — no new packet type constant was found in
the 543 body. **Packet ids emitted by the removal path: UNKNOWN** (not traced to the constant
stores here).

### 2.5 Outcome
id_next only if the item exists, is non-expiring, has neither bit0 nor bit1 of column 19 set,
is not forbidden-to-sell, has column 23 == 0, and the removal call returns true.
Otherwise **id_nextfail** (0x140126a16; plus the 0x140126a18 variant on the NULL template).
No DB call in the body.

## 3. Type 544 — 0x140126565 .. 0x140126588 (super-flag push to one client)

Body is 6 instructions and tail-jumps into the epilogue, so **the handler's return value is
whatever the callee returns** (`jmp 0x140126a18`, AL preserved).

```
140126565  mov  ecx,[rsi+0x48]        ; this->field_0x48 = process id of the map group
140126568  call 0x140008520           ; CMapGroup::IsValidMapGroupProcessID(idProcess) -> CMapGroup*
14012656d  rcx = rax
140126570  call 0x140117f70           ; -> mapgroup->m_pSuperFlagMgr ([mapgroup+0x128])
140126575  rcx = rax (sfMgr)
140126578  r8d = [rsp+0x818]          ; 10th argument of the handler (dispatcher r12)
140126580  rdx = r14 (pUser)
140126583  call 0x14020ec80           ; SuperFlagMgr::SendXxx(sfMgr, pUser, id)
140126588  jmp  0x140126a18
```

- 0x140008520: CHECKF `CMapGroup::IsValidMapGroupProcessID(idProcess)` (mapgroup.h).
- 0x140117f70: CHECKF `m_pSuperFlagMgr` (mapgroup.h line 0x14A).
- 0x14020ec80 (`superflagmgr.cpp`): asserts `pUser != NULL`; `FUN_14020ea80(sfMgr, id)` does a
  **red-black lookup by id** (`[rcx+0x40]` tree, key at node+0x18) -> node; then
  `jmp 0x1404149f0(node, user)`.
- **No sscanf, no DB API** — `id` comes from the caller-supplied 10th argument
  (`[rsp+0x818]`, same slot as 543). Which packet field fills it = UNKNOWN (dispatcher-side).

### 3.1 Packet built (`FUN_1404149f0`, superflag.cpp)
| addr | action |
|---|---|
| 0x140414a5c-0x140414a9b | `g_pItemMgr`, `GetItemTemplate([node+4])`; NULL -> return false |

| 0x140414ad2 | `FUN_140451fd0(&pkt, 0, [node+4], ebx)` = Create: **obj+0x8 = 0x83E (packet 2110)**, **obj+0xC = 0x4C (76)**, `buf+0x00` = 0, `buf+0x04` = node id `[node+4]`, `buf+0x14` = column-4 value |
