## Is the 1650/1651/1654 state machine portable without the client text table?

**YES — the server-side state machine never consults any text table.** Evidence:

1. 1650 parses a `%u` and only ever writes it into the outgoing packet at `[msg+0x428]+0x14`
   (0x1401387ce/0x1401387d5). No id -> text lookup exists anywhere in the block
   (0x140138724-0x140138e68); the only `_stricmp`/`strncmp` in the block are 1651's object-name
   compare (0x140138b61) and 1653's `"=="/"set"` compares (from `case 0xa8`).
2. 1651 validates the answer against the **live object** (NPC name string, or `+0x50()` id),
   not against server text. 1653 (`case 0xa8`, 0x140138bc4) gates on
   `state==3 || +0x970!=0` (0x140138bc4-0x140138bd6), parses `"%s %s %d"`
   (`0x14070dc28`, `cmp eax,3/jge` @0x140138c17) and `_stricmp`s only `"=="`/`"set"`.
3. 1652/1654 close with the fixed word 174; no text involved.

**What is actually missing for a faithful port (state machine only — all identified, none a
text table):**

- `0x1402bf900` predicate body semantics (fields `+0x68`, `+0x69`, `+0xb4` of the class-1
  object) — the *behaviour* used by 1654 is known (compare-to-zero + this predicate), its
  meaning is **UNKNOWN**.
- `0x14038e270(obj, 1)` — the class-2 mutation in 1654's `+0x974==2` branch. **UNKNOWN**.
- The **producer of state 2**: the only other writer of `+0x968` in the module is
  **0x140367333** (`1 -> 2`, and `+0x970 = +0x974 = r15d` at 0x14036733a/0x140367341), inside the
  map/user message handler covering ~0x140366f00..0x140368095. Without that producer the `==2`
  gate of 1651 is unreachable; the meaning of `r15d` there is **UNKNOWN** in this pass.
- Field meanings of `+0x96c` (written only by 1650/1651, never read inside this block) are
  **UNKNOWN** — no reader was found, so it is safe to keep as an opaque dword.

**Only if the port wants to render the dialog server-side** does the client text table matter:
the `+0x14` word of the 171 packet is an opaque index into the **client** text/`cq_action`
dialog tables (`data/`, not in MsgServer.exe), and the NPC-less packet (`+0x08 = 0`) means the
client is expected to resolve that index itself. Porting the machine needs nothing from it;
porting the *content* of the dialog does.
