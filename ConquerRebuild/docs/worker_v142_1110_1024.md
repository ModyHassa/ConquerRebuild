## 1. `0x140087790` — fully decoded: it is a getter, not a stub

The v138 note ("no literals, no direct calls in its first 0x170 bytes") is **wrong** — the function
is only **0x41 bytes long** and ends with `ret` at `0x1400877d0`; everything after that is padding
(`cc` at 0x1400877d1-0x1400877df) and then the *next* function (`0x1400877e0`, which is the
`m_pMagicManager` getter). The v138 range 0x170 straddled several unrelated functions, which is why
"no literals" was reported.

Whole body, 0x140087790..0x1400877d0:

```
0x140087790  sub  rsp,0x38
0x140087794  mov  rax,[rcx+0x230]        ; the field
0x14008779b  test rax,rax
0x14008779e  jne  0x1400877cc            ; non-null -> return it
0x1400877a0  lea  r9 ,0x1406dc180        ; "f:\version\cqserver-78.0.11-1204\msgserver\mapgroupkernel\mapgroup.h"
0x1400877a7  lea  r8 ,0x1406f3b40        ; "m_pNpcPathTaskMgr"
0x1400877ae  lea  rdx,0x1406d9f0c        ; "CHECKF"
0x1400877b5  lea  rcx,0x1406d9c10        ; "¡ï%s(%s)¡ï in %s, %d"
0x1400877bc  mov  dword [rsp+0x20],0x143 ; line 323
0x1400877c4  call [0x1406d8348]          ; assert/log
0x1400877ca  xor  eax,eax                ; -> NULL
0x1400877cc  add  rsp,0x38
0x1400877d0  ret
```

So **`0x140087790` = `CMapGroup::GetNpcPathTaskMgr()`**, an inline accessor returning
`this+0x230` (`m_pNpcPathTaskMgr`) with a `CHECKF` guard, no vtable call of any kind. It is the
sibling of the accessors that follow it byte for byte (`0x1400877e0` -> `+0x100 m_pMagicManager`
literal `0x1406f3b58`, `0x140087830` -> `+0x108 m_pTexasMgr` `0x1406f3b68`, `0x140087880` ->
`+0x120 m_pInstanceMgr` `0x1406f3b78`, `0x1400878d0` -> `+0x140 m_pAuraMgr` `0x1406f3b88`,
`0x140087920` -> `+0x138 m_pTeamDiceMgr` `0x1406f3b98`).

## 2. The "provider" in 1110 is NOT a constant id

The task brief expected a `mov ecx,<imm>` before `0x140008520`. There is none:

```
0x14012a947  mov  ecx,[r12+0x48]   ; mapgroup process id of the action context
0x14012a94c  call 0x140008520
0x14012a951  mov  rcx,rax
0x14012a954  call 0x140087790      ; -> [rax+0x230] m_pNpcPathTaskMgr
```

`0x140008520` (`ecx` = process id) is proven to be the **CMapGroup array lookup**:
it calls `0x1400084e0`, whose bounds check is guarded by the literal `0x1406dc150` =
`CMapGroup::IsValidMapGroupProcessID(idProcess)` (assert at `0x140008555`, line `0x379` = 889), and
returns `&array[id]` with **stride `0x850`** (`imul rbx,rbx,0x850` at 0x1400085a1). So the object that
`0x140087790` is applied to is *the map group the action is running in*, and the "provider id" is
`context->[+0x48]`, i.e. data-driven, never an immediate.

**No vtable slot is called on the returned provider.** `0x1402a74b0` is a direct (non-virtual) call.

## 5. 1024 = DIVORCE (5 rows) — PORTED in v144
`DAT_14013aa9c[1024-1001] = 18`, `body = 0x140000000 + u32[0x14013a7ac+18*4] = 0x14012fd3d`, which is
three instructions: `mov rcx,r13; call 0x140173e20; jmp epilogue` - the action returns `0x140173e20`'s AL.
All five rows have `data=0, param=''`, so **1024 takes no parameters**.
`0x140173e20` (rbp = player), traced:
