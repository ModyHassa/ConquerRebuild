# worker_v122 — action types 1072 and 1043 (closed / partly closed)

Binary: `../conquer_source/Source/MsgServer.exe` (PE32+ x86-64, imagebase
0x140000000). Router `FUN_14012a6e0`: `case = byte_map[0x13aa9c + (type-1001)]`,
`body = 0x140000000 + u32[0x13a7ac + case*4]`.

## 1072 — CLOSED, ready to port

Body **0x14012d507**. No DB access, no string parse.

1. Item identity = **the action's `data` column**. The body calls
   `pAction->vt[0x10](4)` (0x14012d5xx) — vtable slot 0x10 is the column getter and
   index 4 is `data` in `cq_action` (0=id,1=type,2=data,3=param,... as mapped by the
   other cases).
2. `SetInfo(id, x, y)` returns **false when id == 0**, and the caller then skips the
   send. So `data=0` is a silent no-op, not an error.
3. Position comes from the player object itself: `CUser` vtable `+0x40` = X,
   `+0x48` = Y (the same two getters the walk/teleport code uses).
4. The packet is `CMsgMapItem` **1101** with **action 0x0D** (13), `data = 0`,
   `ext = 0`, time = now, coordinates = the player's own cell.
5. Sent to **the executing player only** (`vt +0x350` is the single-session send,
   not the screen broadcast).
6. The body returns **true**, so the chain always takes `id_next`.

Net effect: "put a ground-item marker with the id from `data` under the player's
feet, visible to him only". A faithful port needs no DB and no extra state.

## 1043 — half closed (packet corrected)

Body **0x140135433**. **Correction to the earlier note:** the packet is
**10010 CMsgAction action 110** (0x271A), NOT 10017. The per-element mapping:

- `data` field of the packet = `u32 @ elem+0x10`
- before the send: `+0x19 = max(+0x19, +0x18)`, then `+0x1a = 1`
- after the send the element is **erased** from the container
  (container `vt+0x28`)
- the container lives at `user+0x1110`; the iteration walks it in order

Element shape (from every read in the body):

```
struct Elem {
  /*+0x00..0x0F*/ unknown
  u32  data;      /*+0x10*/
  u8   a18;       /*+0x18*/
  u8   a19;       /*+0x19*/   max(a19, a18) before the send
  u8   a1a;       /*+0x1a*/   set to 1 before the send
  void* p20;      /*+0x20*/
  u8   b28;       /*+0x28*/
};
key getter = 0x14039d9d0
```

UNKNOWN: the element's semantic type, because the writers of `user+0x1110`
(`0x1401cbafc`, `0x1401d186b`) and the body of `0x14039d9d0` are still
unidentified. Closing this needs those three functions, so 1043 stays BLOCKED for
the port while the wire format is now settled.
