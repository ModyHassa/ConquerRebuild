## 4. The biggest body: `case 0xdad` = type 3501 (MsgServer.c 220585-220903)

### 4.1 Argument plumbing
- `param_3` is the action's **`param` column** string; `param_4` is the acting player object
  (`NULL` → `"log_InlineLogERROR"` at 220586-220588, `return false`).
- 220597-220598: `local_740 = local_738` (int*) and `local_748 = &local_730` (uint*) are set
  immediately **before** `sscanf`, i.e. the decompiler is showing the *declared* destination
  slots; the format at 220599 is `"%s %s %I64d %u"`.
  - target 1 = `local_658[256]`  → SUBJECT
  - target 2 = `local_558[256]`  → OPERATOR
  - target 3 = 64-bit (`%I64d`)  → value readback, in the **money** branch used as
    `CONCAT44(uStack_72c, local_730)` (a 64-bit pair at 220839/220854/220868/220883/220898)
  - target 4 = `uint %u`         → `local_730`; in the rank/star_tower branches `local_730`
    is the compared imm8 and the value passed to the setter (`(char)local_730`)
  - `< 3` converted → `"Wrong param number"` DBERROR + `return false` (220600-220607).
- Player key (220592-220596): `param_4->vtbl+0x8` (player id) → `plVar11->vtbl+0x128`
  = "resolve family member/index"; **0 → `return false` immediately** (silent, no log).
  `local_738[0]` (int) holds that resolved key and is the per-branch argument.
- Family-module gate (220567-220579): `CurrentInstanceGet()->vtbl+0x20, 8` must be non-null,
  else `"Family module is not loaded!"` + `return false`.

### 4.2 Three subjects, five operators — all verified by `_stricmp` order
`_stricmp(local_558, X)` at 220608 / 220731 / 220824 → subjects **`"rank"`**, **`"star_tower"`**,
**`"money"`**. Operators are 2- or 3-byte `memcmp`-style loops from `local_658`:
`">"` (220611-220626), `"=="` (220627), `"+="` (220644), `"-="` (220674), `"="` (220704).

| subject | read | read+write | block |
|---|---|---|---|
| rank | `vtbl+0x160` (imm8 getter) | `vtbl+0x168` (imm8 setter) | 220608-220729 |
| star_tower | `vtbl+0x150` | `vtbl+0x158` | 220731-220822 |
| money | `vtbl+0x198` (int64 getter) | `vtbl+0x1a0` (set), `vtbl+400` (offset add) | 220824-220902 |

Exact semantics per operator:
- `rank >`  → `return (int)local_730 < (int)(get8 & 0xff)`  (220625) — i.e. **value > N**
  since the stored field is returned in the low byte.
- `rank ==` → `return (get8 & 0xff) == local_730` (220641)
- `rank +=` → **new = old + imm8; if new > 4 → `"Wrong param"` + false** (220655-220663);
  else `set8(key, old+imm)` and return its bool (220668-220671). Bound **4** at 220657.
- `rank -=` → if `old - imm < 0` → `"Wrong param"` + false (220678-220686); else
  `set8(key, old-imm)` (220697-220700). Bound **0**.
- `rank =`  → **if `local_730 < 5`** → `set8(key,(char)imm)` (220706-220710); else
  `"Wrong param"` + false. So the legal rank range is **0..4** (5 states).
- `star_tower` is identical but on `+0x150`/`+0x158` **with no range checks at all**
  (no `Wrong param` path in that block: 220734-220821) — the tower star count is unchecked.
- `money >`  → `return CONCAT44(uStack_72c,local_730) < get64(key)` (220839)
- `money ==` → `return get64(key) == value64` (220854)
- `money +=` → `vtbl+400(key, value64)` (220868) — no bound check (no "Wrong param")
- `money -=` → `vtbl+400(key, -value64)` (220883) — implemented as a **negated add**
- `money =`  → `vtbl+0x1a0(key, value64)` (220898)

Vtable slots `+0x150/+0x158` (8-bit tower-star get/set), `+0x160/+0x168` (8-bit rank get/set),
`+0x198` (int64 money get), `+0x1a0` (int64 money set), `+400` (=0x190, int64 money add) are
read off the same family-object vtable `plVar11` — object semantics for 0x150/0x160 are proven
only by *use* (read-only vs read+write pairing), the field identity is **UNKNOWN** beyond
"rank-like byte" / "star-tower-like byte".

### 4.3 Outcome / packet
- **No packet is sent.** A `grep` for `0x350` / `SendPacket` / `FUN_14015b300` / `SendMsg`
  over 220585-221060 returns zero hits: 3501 is a **pure test/mutate action** with no
  client-facing message. (Contrast: the 320 special path at 223596 does use
  `FUN_14015b300(...,"SYSTEM",...)`.)
- Branch outcome is the plain bool: **true → slot 1 `id_next`**, **false → slot 2
  `id_nextfail`** (engine 223778-223785). This is the documented multichain pattern and it
  matches the DB: `rank = 0` chains like 5022310→5022320 (pass) / →5022311 (fail).
- The engine also does NOT abort: `FUN_140140380` returns false and the loop just follows
  `id_nextfail`; false is not an error.
- Timing/loop guard (223760-223775): per-type time is accumulated into
  `DAT_140975db0`; >100 ms or >10000 ms total, or >999 ms single, logs
  `"CGameAction::ProcessAction over time"`. Max 0x20 (32) hops then
  `"...too many game action"` (223787-223792).

### 4.4 DB reality check for 3501 (`mysql -uroot cq`)
- 81 rows, **all 81 have exactly 3 whitespace tokens** — matches `sscanf` returning 3
  (the 4th `%u` is never supplied; `local_730` therefore keeps whatever it was, which is why
  the `rank =`/`+=`/`-=` forms (6 rows) work off a stack value — the parser never fills it
  from text unless a 4th token exists. **UNKNOWN** whether the original intends 4 tokens;
  no DB row exercises 4).
- Subject/operator histogram: `rank ==` 22, `star_tower ==` 18, `rank >` 15, `money >` 8,
  `money +=` 8, `rank =` 6, `star_tower =` 4.

  independently confirming the 0..4 range.
- `id_next = 0` for 0 of the 81 rows (no terminal 3501), `id_nextfail = 0` for 13 — so 13
  rows hard-fall-through on failure (`return false` then no next id).

  3501..3699 goes to `FUN_140140380`.

  (`rank` / `star_tower` / `money` × `> == += -= =`), sends **no packet**, and routes
