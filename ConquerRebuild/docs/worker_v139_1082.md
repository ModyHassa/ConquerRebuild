# 1082 (52 rows) — grammar fully decoded; in real data it is ALWAYS `self add <status> 200 <secs> 0`

## Grammar (from the literals of body `0x14012f025`)
`sscanf(param, "%s %s %u %d %d %d")` (fmt `0x14070f080`) - **two tokens + four numbers**, and the two
tokens are compared with `strcmp` against exactly these literals:

| address | literal | role |
|---|---|---|
| 0x14070f060 | `team`   | token 1: the target scope |
| 0x14070f068 | `couple` | token 1 |
| 0x14070f070 | `mate`   | token 1 |
| 0x14070f078 | `self`   | token 1 |
| 0x14070f2d0 | `add`    | token 2: the operation |
| 0x14070f390 | `chk`    | token 2: the operation |

So the shape is `<team|couple|mate|self> <add|chk|del> <n1> <n2> <n3> <n4>`.

## What the shipped action table actually contains
```
SELECT SUBSTRING_INDEX(param,' ',2), COUNT(*) FROM cq_action WHERE type=1082 GROUP BY 1;
  self add   51
  self del    1
```
and every `self add` row has the constant third field **200** with a duration:
`self add 2 200 10 0`, `self add 6 200 1800 0`, `self add 7 200 3600 0`, `self add 17 200 60 0`, ...

**Conclusion:** for our data set this action is a **timed self status/effect**: status id `<n1>`,
constant `200` (a kind/percent selector), duration in **seconds**, last field 0. The `team` / `couple` /
`mate` branches and the `chk` operation are **never used by any row**, so they are not needed for a
faithful port of this database - but they must be implemented as the original's "no-op/fail" path only
if we later need to be exact for those inputs.

## Couple model confirmed in the schema
`cq_user.mateid INT(4) UNSIGNED DEFAULT 0` exists (the only mate/couple column in the whole DB - there
is no couple/spouse table). That is what the `mate`/`couple` branches would operate on.

## Still needed before implementing
The **effect** of `add` on self: which manager/slot receives (status, 200, seconds) and what packet is
sent. The body calls `0x140512630` (twice, near the top), `0x1401181a0`, then a vtable `+0x8` call,
and reads its parsed values back off the stack (`0x10c(%rsp)`, `0x110(%rsp)`, `0x11c(%rsp)`). Reading
that path is one focused step and is the only thing left for these 52 rows.

## The `self add` call site, proven argument by argument

`0x14012f0fc` compares token 2 with **`add`**; on match (`0x14012f115..0x14012f16f`):

```
call 0x1401181a0            ; GetInstance(slot 0x14) = status::CStatusMgr (HANDOFF v124)
rdi = mgr ; rsi = [mgr]     ; the Status.dll vftable 0x1416da0f8
call [r13]->vt[+0x8]        ; eax = the acting object's slot 8 result  -> arg2 (actor)
edx = eax
[rsp+0x20] = &n3            ; lea 0x10c(%rsp)
[rsp+0x28] = &n4            ; lea 0x110(%rsp)
r9d  = n2                   ; 0x11c(%rsp)
r8d  = n1                   ; 0xc8(%rsp)
[rsp+0x30..0x50] = 0,0,0,(word)0,(int)0
call [rsi]->vt[+0x8]        ; CStatusMgr::AddStatus  (11 args, 7 on the stack)
```

and the `sscanf` destination mapping at `0x14012f082..0x14012f0b1` is explicit:
`[rsp+0x20]=&0xc8`, `[rsp+0x28]=&0x11c`, `[rsp+0x30]=&0x10c`, `[rsp+0x38]=&0x110`, so with
`"%s %s %u %d %d %d"`: **n1 = the `%u`, n2/n3/n4 = the three `%d`**.

Therefore 1082 issues
**`AddStatus(actor = actorObj->vt[8](), a3 = n1, a4 = n2, a5 = n3, a6 = n4, a7 = 0, a8 = 0, a9 = 0, a10 = 0, a11 = 0)`**,
`chk` issues `actorObj->vt[+0x2d8](n1)` and returns its value, and any other token issues
`AddStatus`' sibling `vt[+0x10]` (= `ApplyUserStatusCode`) with `n1`.

## CONFLICT with docs/worker_v125_statusmgr.md - must be settled before coding
v125 proved from Status.dll that AddStatus' args fill the record as
`arg4=t1, arg5=t5, arg6=t4, arg7=t2, arg8=t3 (t3 is the duration: rec+0x18 = now + t3), arg9=t6`.
Applying that to this call site gives, for `self add 7 200 1800 0`:
`targetField = 7, t1 = 200, t5 = 1800, t4 = 0, t2 = 0, t3 = 0, t6 = 0` - i.e. **`t3`, the proven
duration, is 0** while the obvious duration-looking number (1800 / 3600 / 1200) lands in `t5`.
Two readings are possible and **neither is proven**:
1. the duration for *this* caller really is 0 and `t5` means something else (e.g. a repeat/count), or
2. the v125 arg numbering is off by one slot for this call site.
**Do not implement until Status.dll's `AddStatus` prologue is re-read** (vftable `0x1416da0f8`, slot 8,
prologue around `0x1416be0..0x1416be1..`): one focused read settles which arg reaches `rec+0x18`.
Everything else about 1082 is now measured: grammar, scope/op token sets, real-data distribution
(51x `self add`, 1x `self del`), the singleton (slot 0x14 = `status::CStatusMgr`), the slots used
(`+0x8` add, `+0x10`, `+0x2d8` chk), and the exact value plumbing.

## v140 — IMPLEMENTED (52 rows). The conflict is settled: the duration really is 0

Read Status.dll's `AddStatus` itself (`GetInstance(0x14)` vtable `0x1416da0f8`, slot `+0x8` ->
**`0x1416be020`**, image base `0x1416b0000`). Its prologue stores, instruction by instruction
(record base = `[rsp+0x48]`, args 5+ at `[rsp+0xC0]`, `0xC8`, ... after `push*5` + `sub rsp,0x70`):

| record | source | instruction |
|---|---|---|
| +0x00 | 0 | `mov DWORD [rsp+0x48],ebx` (ebx=0) |
| +0x04 | **arg2** (edx) | `mov DWORD [rsp+0x4c],r12d` |
| +0x08 | **arg3** (r8d) | `mov DWORD [rsp+0x50],esi` |
| +0x0c | **arg4** (r9d) | `mov DWORD [rsp+0x54],r15d` |
| +0x10 | computed flags | `[rsp+0x58]` |
| +0x11 | **(byte)arg6** | `mov BYTE [rsp+0x59],bl` (bl = `[rsp+0xC8]`) |
| +0x14 | **arg7** | `mov DWORD [rsp+0x5c],edx` (edx = `[rsp+0xD0]`) |
| +0x18 | **time(0) + arg8** | `call time; add eax,[rsp+0xD8]; mov [rsp+0x60],eax` |
| +0x1c | **arg5** (+1 when arg3==0x12) | `mov eax,[rsp+0xC0]; inc` / `mov [rsp+0x64],eax` |
| +0x20 | **(byte)arg9** | `movzx eax,BYTE [rsp+0xE0]; mov [rsp+0x68],al` |
| +0x24 | **arg11** | `mov eax,[rsp+0xF0]; mov [rsp+0x6c],eax` |

So **v125's arg order is correct**, and 1082's caller genuinely passes `arg8 = 0`: for
`self add 7 200 1800 0` the real values are `arg3 = 7`, `t1 = 200`, `t5 = 1800`, `t4 = 0`,
`t2 = 0`, **`t3 = 0`** (expiry = now), `t6 = 0`. The 1800 is an opaque `t5`, not the duration.
Note `arg10` is not a constant either - the prologue tests it (`cmp ax,0x1`) to compute the flags
byte, so 1096's `1` was a caller value.

Also proven: only **arg2** is range-checked as a player id (`lea eax,[rdx-0xf4240]` /
`cmp eax,0xee5be5bf` / `ja` at `0x1416be055`), so the small `arg3` (2/6/7/17) can be the status
rather than a user. And the action returns **TRUE** for the add branch (`mov al,0x1` at
`0x14012f761`); a `<6`-conversion parse falls to the shared "bad parameter count" log
(`0x14070c010`, err `0x20d6`) and FALSE.

Implementation: `src/systems/actions.hpp` `case 1082` -> `StatusSystem::add(p.id, p.id, t1=n2,
t5=n3, t4=n4, t2=0, t3=0, t6=0, type=n1)`. The `team`/`couple`/`mate` scopes, `chk`
(`actorObj->vt[+0x2d8](n1)` on an unidentified object) and the `vt[+0x10]` apply path are
**BLOCKED and refused** rather than guessed - no shipped row uses them (51x `self add`, 1x
`self del`, and `del` is not even one of the compared tokens so it takes the apply path).
Test: `tests/test_actions_v140.py` (5 checks) proves the effect end to end by running a **1098
mode-0 probe before and after the add inside one click chain** (statuses are memory-only, so a
re-login would drop them), plus the bad-count and blocked-scope branches.
