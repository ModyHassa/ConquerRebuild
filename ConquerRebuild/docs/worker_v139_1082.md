# 1082 (52 rows) — grammar fully decoded; in real data it is ALWAYS `self add <status> 200 <secs> 0`

## Grammar (from the literals of body `0x14012f025`)
`sscanf(param, "%s %s %u %d %d %d")` (fmt `0x14070f080`) - **two tokens + four numbers**, and the two
tokens are compared with `strcmp` against exactly these literals:

| address | literal | role |
|---|---|---|
| 0x14070f060 | `team`   | token 1: the target scope |
| 0x14070f068 | `couple` | token 1 |
| 0x14070f070 | `mate`   | token 1 |
| 0x14070f078 | `self`   | token 1 |
| 0x14070f2d0 | `add`    | token 2: the operation |
| 0x14070f390 | `chk`    | token 2: the operation |

So the shape is `<team|couple|mate|self> <add|chk|del> <n1> <n2> <n3> <n4>`.

## What the shipped action table actually contains
```
SELECT SUBSTRING_INDEX(param,' ',2), COUNT(*) FROM cq_action WHERE type=1082 GROUP BY 1;
  self add   51
  self del    1
```
and every `self add` row has the constant third field **200** with a duration:
`self add 2 200 10 0`, `self add 6 200 1800 0`, `self add 7 200 3600 0`, `self add 17 200 60 0`, ...

**Conclusion:** for our data set this action is a **timed self status/effect**: status id `<n1>`,
constant `200` (a kind/percent selector), duration in **seconds**, last field 0. The `team` / `couple` /
`mate` branches and the `chk` operation are **never used by any row**, so they are not needed for a
faithful port of this database - but they must be implemented as the original's "no-op/fail" path only
if we later need to be exact for those inputs.

## Couple model confirmed in the schema
`cq_user.mateid INT(4) UNSIGNED DEFAULT 0` exists (the only mate/couple column in the whole DB - there
is no couple/spouse table). That is what the `mate`/`couple` branches would operate on.
