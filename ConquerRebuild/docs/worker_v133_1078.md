# 1078 — the e-money card redeem action (7 rows) — decode in progress

Case 0x44 body `0x14012c01b..0x14012c046` is five instructions plus the return:

```
14012c01b  rcx = *(%r15) ; rax = *(%rcx)          ; the action record wrapper
14012c021  edx = 4 ; call *0x10(%rax)             ; ctx slot 4
14012c029  rdx = *(%rax) ; rcx = %rax
14012c02f  call *0x48(%rdx)                       ; -> the id (`data` column = id4)
14012c034  rcx = user (r13) ; edx = id4
14012c037  call 0x1401ac210                       ; CUser::RedeemEmoney(type = id4)
14012c03c  test %al,%al ; je fail
14012c044  return TRUE
```

So **1078 = `0x1401ac210(player, a->data)` and the action result is its return value.** No
parsing of `param`, no state, no packet of its own.

## What `0x1401ac210` is (verified from its own literals)
`.rdata` strings inside the function:

- `0x1407176e8` = `SELECT * FROM %s WHERE account_id=%u && used=0 && type=%d`
- `0x140714500` = `emoney_card`
- `0x140714d90` = `f:\version\cqserver-78.0.11-1204\msgserver\mapgroupkernel\user.c`

so it looks up an **unused `emoney_card` row of the given type for the player's account**, reads one
field at a time through a row accessor (`vt[0x20](key)` + `vt[0x40]`, the same keyed-row idiom the
date container uses), and on any miss logs at `user.c:0x4b02` (`0x1406dbfa0`/`0x1406e5370`) and
returns false.

The live schema matches: `emoney_card(id, type, account_id, ref_id, chk_sum, time_stamp, used,
ordernumber, flag)` with `used` defaulting to 1.

## Still UNKNOWN before the port (2 facts)
1. **Which column the card credits** (the value field read after the query, and whether it lands in
   `cq_user.emoney_mono` - the container field at `+0x1BC` - or in `money`/points).
2. **The exact write-back**: whether it updates `used=1` (and `time_stamp`), and whether it inserts
   an `emoney_used`/log row.
Both are inside the 0x1401ac2xx body and are the only things standing between this doc and a port.

# `CUser::RedeemEmoney` (0x1401ac210) — full validated flow (this wave)

Everything below was read from the body; the only remaining gap is marked UNKNOWN.

```
row = RunQuery("SELECT * FROM emoney_card WHERE account_id=%u && used=0 && type=%d")
      (0x1407176e8 / 0x140714500); NULL -> log @user.c:0x4b02 -> false
ref_id    = row.int("ref_id")      (0x1406de6e8)  -> r14d   (0x1401ac342)
time_stamp= row.int("time_stamp")  (0x140717678)  -> [rsp+0x3c]
chk_sum   = row.int("chk_sum")     (0x1406de6e0)  -> ebx
type      = row.int("type")        (0x1406de6d4)  -> eax
price     = 0x140276390(singleton, type)   ; must be > 0 else fail (0x1401ac3b2..c0)
if (0x140164640(account_id, ref_id, time_stamp, 0) == chk_sum)  goto ACCEPT
else if (((account_id ^ 0xBE6E0) + (ref_id >> 1)) == chk_sum)   goto ACCEPT
else log 'Check %s chksum failed. AccountID=%u, RefID=%u' (0x140719468) / 'chksum is old'
     (0x140719420) and free the row -> false

ACCEPT (0x1401ac486):
  now      = <time>()                                        ; ebx
  new_sum  = 0x140164640(account_id, ref_id, now, 1)          ; edi
  row.set_int("used", 1)            (0x140717878, vt+0xb0)
  row.set_int("time_stamp", now)    (0x140717678, vt+0xa8)
  row.set_int("chk_sum", new_sum)   (0x1406de6e0, vt+0xa8)
  row.flush(1)                      (vt+0x38)
  credit: user->[0x10]->vt[0x2e0](...) then 0x1401742b0(...)  ; **the grant, see UNKNOWN**
  log 'gmlog/card_checkout' "Checkout card1 userid:%u user_name:%s idRef:%u price:%d"
      (0x1407193c8 / 0x1407193e0)
  -> true
```

So the card is **used up in the same call that validates it**: `used=1`, `time_stamp=now`,
`chk_sum` re-stamped with the `flag=1` variant of the checksum. The two accepted checksums are the
strict one (`flag=0`) and the legacy `(account_id ^ 0xBE6E0) + (ref_id >> 1)` form.

## The ONE remaining UNKNOWN before the port
`0x1401742b0` (reached with `%r15d` = `price`) - the actual **credit**. `0x140276390(singleton, type)`
returning `price` is the card's value, and the value must be positive for the action to proceed, but
whether `0x1401742b0` adds to `cq_user.money`, to `emoney_mono` (`CUser+0x1BC` in the date
container), or to a points counter is **not yet proven**. Until that call is identified, porting 1078
would grant the wrong currency, so it stays BLOCKED - one function away.

`0x140164640(account_id, ref_id, timestamp, flag)` is the checksum helper both paths use; its body is
also unread (it is deterministic, so it must be ported exactly rather than approximated).
