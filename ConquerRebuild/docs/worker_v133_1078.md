# 1078 — the e-money card redeem action (7 rows) — decode in progress

Case 0x44 body `0x14012c01b..0x14012c046` is five instructions plus the return:

```
14012c01b  rcx = *(%r15) ; rax = *(%rcx)          ; the action record wrapper
14012c021  edx = 4 ; call *0x10(%rax)             ; ctx slot 4
14012c029  rdx = *(%rax) ; rcx = %rax
14012c02f  call *0x48(%rdx)                       ; -> the id (`data` column = id4)
14012c034  rcx = user (r13) ; edx = id4
14012c037  call 0x1401ac210                       ; CUser::RedeemEmoney(type = id4)
14012c03c  test %al,%al ; je fail
14012c044  return TRUE
```

So **1078 = `0x1401ac210(player, a->data)` and the action result is its return value.** No
parsing of `param`, no state, no packet of its own.

## What `0x1401ac210` is (verified from its own literals)
`.rdata` strings inside the function:

- `0x1407176e8` = `SELECT * FROM %s WHERE account_id=%u && used=0 && type=%d`
- `0x140714500` = `emoney_card`
- `0x140714d90` = `f:\version\cqserver-78.0.11-1204\msgserver\mapgroupkernel\user.c`

so it looks up an **unused `emoney_card` row of the given type for the player's account**, reads one
field at a time through a row accessor (`vt[0x20](key)` + `vt[0x40]`, the same keyed-row idiom the
date container uses), and on any miss logs at `user.c:0x4b02` (`0x1406dbfa0`/`0x1406e5370`) and
returns false.

The live schema matches: `emoney_card(id, type, account_id, ref_id, chk_sum, time_stamp, used,
ordernumber, flag)` with `used` defaulting to 1.
