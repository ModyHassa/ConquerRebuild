## 2. THE OBJECT — it is NOT held by the player — VERIFIED

Both bodies fetch it identically, and neither reads any user field to find it:

```
14013ca2c1..cb16 (218) / 14013cb57..cb16 (219):
  call [rip+...]  -> 0x1406d8df0          ; imported service getter (same IAT slot that
                                          ;  FUN_1401181a0 uses, see worker_v122_shared_helpers.md §1)
  mov  edi,[rax]                          ; service vtable
  mov  edx,0x8                            ; component id = 8
  mov  rcx,rax
  call [rdi+0x20]                         ; service->vt[0x20](8)  -> the object
  test rax,rax ; je 0x14013d6ff           ; NULL -> return false
```

Answers to the four questions asked:

* **Which player slot holds it:** *none*. It is a **process-wide service component obtained by
  numeric id 8** (`GetService()->vt[0x20](8)`) on every call — not cached in a static, not
  stored in the player object, not read out of `param_2`/`param_4`. The player is used only for
  `GetID()` and for delivering the error message. So there is no "player slot" to port; the
  port needs a service-registry lookup `get_component(8)`.
* **How it is created:** lifecycle is the service factory's, not these actions'. Neither body
  constructs it (no allocator call, no ctor) — only `vt[0x20](8)` and a NULL check.
* **The CHECKF string naming it:** `pUser` (0x1406e9e78) names the *player*, not the component.
  The component has **no CHECKF string in either body** — it is only NULL-tested and silently
  returns false. UNKNOWN: no name string is asserted on the component.
* **vtable slots used:** see per-type tables below. Component slots: **0xf0** (218),
  **0x128** and **0x100** (219). Player slots: **+0x8** (GetID) in both; **+0x358** (send
  string to player) in 218 only.

### 2.1 Is it a "family" object? — PARTIAL, identity of id 8 = UNKNOWN

Proven family-flavoured evidence: the **only** string 218 can emit to the player is
**`"STR_INVALID_FAMILY_NAME"`** — literal at **0x14070faa8**, loaded at `0x14013cac4`.
That is the sole semantic anchor; it is strong but it is a message name, not proof of the
manager's type.

Counter-constraint: **220 (0xdc) uses the same component id 8** (`0x14013cbb4`+) with slot
**0x108**, so id 8 is a multi-purpose manager, not a 218/219-only object.

UNKNOWN: the C++ type behind component 8. NOT PROVEN: a link to the `"Family module is not
loaded!"` literal (VA 0x1407104b6) — a full-text xref scan of `.text` found **no reference**
to that address, so it must not be cited as belonging to these handlers.

**Verdict on the premise:** the premise "both need an unidentified family object" is
**half right**. They do need one unidentified object — but it is a **service component id 8**,
not a *family system* in the sense of a per-player family record store. There is **no family
slot, no family id read from the user, no family table (cq_family) access** in either body.
If the port has no service registry, the correct minimal port is a single
`get_component(8)` hook with three virtuals (`vt[0xf0]`, `vt[0x128]`, `vt[0x100]`), plus the
one string-table lookup for `STR_INVALID_FAMILY_NAME`.

### 3.1 What 0x14008a1d0 actually is — VERIFIED, thin

`FUN_14008a1d0(a,b,c)` in the C listing is a **one-line forwarder**:
`{ FUN_1400fb570(param_2, param_3); }` (MsgServer.c:100800). So the call is
`FUN_1400fb570(name, 0)`, whose prologue (`0x1400fb570`) loads the global at
**0x140975cd0** and does bound-checked compares of two pointers (`[rdi]`,`[rdi+0x18]`,
`[rdi+0x20]`) before a copy into a 0x10-byte local — i.e. a **name lookup in a string/key
container**, returning non-zero when found. Practical meaning: the check is
"**is this name already taken / reserved?**" → non-zero = collision = `STR_INVALID_FAMILY_NAME`.
UNKNOWN: the exact container (`0x140975cd0`) and whether "found" means taken vs. forbidden.

**sscanf format: NONE. No string argument at all** — the body is driven purely by the

**Operations:** two-phase id-only operation on component 8 — a **predicate** on slot 0x128

(two separate virtual calls, no caching).

**Packets built: NONE.** No CMsg* construction anywhere in the body; no message is even sent
to the player on failure (silent `return false`).

**Branch outcome:** 4 exits — CHECKF-false, NULL-component-false, `vt[0x128]==0`-false,
else `vt[0x100]`'s boolean.

UNKNOWN: semantics of 0xf0/0x128/0x100. The shape (predicate-then-action, both keyed by user
id, no name) is consistent with 219 = "**enter/leave or claim/release** the 218-created
entity for this player", but the slot meanings are NOT proven and must not be asserted.

## 5. Port notes / gaps

* Neither type requires a `family` data model to be *dispatched*. Both need only:
  `component(8)` with `vt[0xf0](uint,const char*)`, `vt[0x128](uint)->int`,
  `vt[0x100](uint)->bool`; a name-collision lookup; one localized string.
* 218 is the **only** one that emits a packet-ish side effect (system message via user
  `vt[0x358]`), 219 is silent. Neither returns a `cq_action.id_nextfail`-style value; both
  return a bare bool to ProcessAction, which then falls through to `0x14013d6ff`/`0x14013d701`.
* Not yet present in `src/systems/actions.hpp` (searched: no `case 218`/`case 219`), so both
  are still unported as of this file.
* Still UNKNOWN: identity of component 8; container at 0x140975cd0; whether 0x1400fb570's
  non-zero means "taken"; all three component vtable slot semantics.
